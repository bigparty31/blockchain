**주요 로직**

- **장부 잔액은 서버 합계를 쓰지 않고 항목에서 직접 계산한다** (PRD §7.4 `Σ확정수입 − Σ확정지출`).
  서버가 내려준 합계를 그대로 표시하면, 서버가 숫자를 바꿨을 때 학생이 알 방법이 없다.
- `PENDING` 건은 합계에서 제외한다. 승인 전 금액이 학생 화면 수치에 섞이면 안 된다.
- 계좌 차액은 **경고만** 한다. 오픈뱅킹 조회 결과를 원장에 자동 반영하면 대조 대상 자체가 사라진다 (PRD §7 규칙 7).

## 3. 표시 로직 구현

### 3.1 검증 배지 (S4) — `app/lib/core/meta_hash.dart`

`meta_hash = SHA256(amount | counterparty | purpose | occurred_at | receipt_hash)` 를
**앱 안에서 다시 계산해** 온체인 값과 대조한다.

| 상태 | 조건 | 표시 |
|:---|:---|:---|
| `verified` | 재계산 == 온체인 | 초록 「검증됨 · 기록 변경 없음」 |
| `tampered` | 재계산 ≠ 온체인 | 빨강 「변조 감지 · 등록 후 내용이 바뀜」 |
| `unavailable` | 온체인 해시 없음 | 회색 「검증 불가 · 대조할 기록 없음」 |

**설계 근거 (PRD §7.3)**

- 검증 로직은 **앱 배포본에 내장**한다. 서버가 내려주는 코드로 검증하면 서버 장악 시
  항상 통과를 반환하도록 바꿀 수 있다. → 서버 응답으로 이 규칙을 바꾸는 코드를 추가하지 말 것.
- `unavailable` 은 **「통과」가 아니라 「모름」**이다. 삭제 공격은 검증 실패가 아니라
  데이터 없음으로 나타나기 때문에, 회색을 초록과 같이 취급하면 안 된다.
- **OCR 판독값은 해시에 넣지 않는다** (PRD §6). 엔진을 교체하면 판독값이 달라져
  기존 검증 배지가 전부 깨진다.
- 비교 시 `0x` 접두사와 대소문자 차이는 정규화한다. 표기 차이는 변조가 아니다.

### 3.2 「OCR 불일치 상태로 승인됨」 뱃지 (S7)

| OCR 상태 | 뱃지 | 이유 |
|:---|:---|:---|
| `MISMATCH` | 표시 | 금액 불일치인데 승인됨 |
| `DUPLICATE` | 표시 | 중복 영수증인데 승인됨 |
| `NO_NUMBER` | 없음 | 계좌이체 등 정상 경로 |
| `UNREADABLE` | 없음 | 판독 실패는 정상 경로 |
| `MATCH` | 없음 | — |
| `category_warning` | 표시 | 용도 불일치 소프트 경고 |

경고 승인은 **즉시** 학생에게 노출된다 (PRD §285). 결산에만 집계하면 4개월 뒤에야
보이므로 억지력이 없다. 승인자가 입력한 사유도 상세 화면에 그대로 보여준다.

### 3.3 정정 이력 병합 (S9) — `app/lib/core/entry_merge.dart`

`corrects_entry_id` 로 원본을 참조하는 항목들을 하나의 체인으로 접는다.
정정의 정정(A ← B ← C)도 끝까지 따라간다.

| 개념 | 규칙 |
|:---|:---|
| 표시 | 원본 금액에 취소선, 최종값 강조. `50,000원 → 30,000원 정정 (입력 오류)` |
| 합계 | **최종값만 반영.** 원본과 정정을 둘 다 더하면 이중 계상된다 |
| 확정 기준 | `CONFIRMED` 인 정정만 값으로 인정. 대기 중 정정은 아직 원본 값이 유효 |
| 고아 정정 | 원본이 목록에 없으면 정정 자체를 체인 머리로 취급 (필터로 잘려도 화면에서 사라지지 않게) |

정정 사유는 `docs/enums.md` 고정 4종(`INPUT_ERROR` / `RECEIPT_RECHECK` / `REFUND` / `RECLASSIFY`)만 쓴다.

### 3.4 예산 개정 이력 (S6)

`version > 1` 인 예산에 `v2` 뱃지와 개정 사유를 붙인다.
개정은 **덮어쓰기가 아니라 버전 추가**이므로 이전 버전이 있었다는 사실 자체가 정보다.

> 현재 `BudgetResponse` 에는 이전 버전 금액이 없어, `행사비 200만 → 250만` 중
> **화살표 앞 금액을 표시할 수 없다.** 현재는 `예산 개정 — 250만원 (v2, 참가인원 증가)`
> 형태로만 표시한다. → §5 백엔드 요청사항 참조.

### 3.5 계좌 차액 경고·미등록 건 (S11)

`차액 = 장부잔액 − 계좌 조회 잔액` (PRD §7.4). 차액이 0이 아니거나 미등록 건이
있으면 경고 카드를 띄운다.

**계좌 대조는 한 방향이다.** 조회 결과를 원장에 자동 반영하지 않는다 —
자동으로 맞춰버리면 대조 대상 자체가 사라져 미등록 지출을 영영 못 찾는다.

### 3.6 미확인 항목 뱃지 카운트 (S12)

마지막으로 확인한 항목 id 를 `flutter_secure_storage` 에 저장하고, 그보다 id 가 큰
항목 수를 대시보드 아이콘에 겹쳐 표시한다. 내역 목록을 열면 지워진다.

## 6. 해시 규칙 확정 대기 (손종인, 9/17 목 오후 예정)

**규칙이 백엔드와 한 글자라도 다르면 모든 항목이 「변조 감지」(빨강)로 뜬다.**
현재 구현은 PRD §8 표기를 그대로 따른 잠정 값이며, `meta_hash.dart` 의
`separator` 와 `canonical()` 만 고치면 전체가 맞춰지도록 격리해 두었다.

확인해야 할 항목:

1. 구분자가 정말 `|` 인지 (`:` 나 빈 문자열일 수도 있다)
2. `amount` 를 문자열로 어떻게 쓰는지 (`35000` / `35,000`)
3. `occurred_at` 이 epoch 초인지 ISO8601 문자열인지
4. `receipt_hash` 가 null 인 수입 항목에서 무엇으로 대체되는지 (빈 문자열 / `0x00..`)
5. 해시 결과 표기에 `0x` 접두사가 붙는지

**대조 방법** — 샘플 항목과 기대 해시를 받아 아래를 호출하고 `true` 가 나오는지 본다.

```dart
MetaHash.matchesSample(
  amount: 35000,
  counterparty: '한결문구',
  purpose: '신입생 환영회 명찰 및 필기구 구매',
  occurredAt: 1757300000,
  receiptHash: '9f2c...',
  expectedHash: '<백엔드가 계산한 값>',
);
```
