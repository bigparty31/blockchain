**주요 로직**

- **장부 잔액은 서버 합계를 쓰지 않고 항목에서 직접 계산한다** (PRD §7.4 `Σ확정수입 − Σ확정지출`).
  서버가 내려준 합계를 그대로 표시하면, 서버가 숫자를 바꿨을 때 학생이 알 방법이 없다.
- `PENDING` 건은 합계에서 제외한다. 승인 전 금액이 학생 화면 수치에 섞이면 안 된다.
- 계좌 차액은 **경고만** 한다. 오픈뱅킹 조회 결과를 원장에 자동 반영하면 대조 대상 자체가 사라진다 (PRD §7 규칙 7).

## 3. 검증 구현 (S4)

`docs/HASHING.md` 규칙 v1 을 따른다. **정본은 그 문서이고 이 절은 앱 쪽 구현 메모다.**

### 3.1 세 단계를 모두 돌린다

**해시 비교만으로는 검증이 반쪽이다.** `HASHING.md` §2 의 실측:

```
지출 35000원, budget_id=2, kind=EXPENSE  -> d8e7c7ae…
kind=INCOME 으로 변조                     -> d8e7c7ae…  (불변)
budget_id=7 로 변조                      -> d8e7c7ae…  (불변)
```

| 단계 | 내용 | 빠뜨리면 |
|:---|:---|:---|
| 1 | 원본 필드로 `meta_hash` 재계산 → `getEntry(id).hash` 와 비교 | 금액·사용처·목적·일시 변조를 놓친다 |
| 2 | `kind`·`budget_id`·`corrects_id`·`status`·`registrant`·`approver` 를 `getEntry(id)` 값과 직접 비교 | **수입↔지출 뒤바꾸기, 예산 항목 옮기기를 놓친다** |
| 3 | 내려받은 영수증 바이트로 `fileHash` 재계산 → `receipt_hash` 와 비교 | **영수증만 바꿔치기한 위조를 놓친다** |

### 3.2 배지 상태는 네 가지다

| 상태 | 조건 | 표시 |
|:---|:---|:---|
| `verified` | 세 단계 모두 통과 | 초록 「검증됨」 |
| `tampered` | 어느 한 단계라도 불일치 | 빨강 「변조 감지」 |
| `partial` | 통과한 것은 이상 없으나 **일부 단계를 돌리지 못함** | 파랑 「부분 검증」 |
| `unavailable` | 대조할 기록이 아예 없음 | 회색 「검증 불가」 |

**`partial` 을 초록으로 만들지 않는 것이 핵심이다.** 확인하지 못한 것을 확인했다고
보여주면 배지의 의미가 없어진다. 마찬가지로 `unavailable` 은 「통과」가 아니라
「모름」이다 — 삭제 공격은 검증 실패가 아니라 데이터 없음으로 나타난다 (PRD §7.3).

**반대 방향의 오탐도 같은 무게로 막는다.** 없는 값을 빈 값으로 바꿔 대조에
집어넣으면, 아직 체인에 안 올라간 정상 항목이 「변조 감지」로 뜬다. 학생이 멀쩡한
기록을 조작된 것으로 읽게 되므로 이쪽이 더 나쁘다.

| 체인에서 온 값 | 뜻 | 배지 |
|:---|:---|:---|
| `hash: null` · `""` · `bytes32(0)` | 아직 기록 전 (채굴 대기) | `unavailable` 「검증 불가」 |
| 0 으로만 채워진 `Entry` struct | 그 id 의 기록이 없음 | 체인 기록 없음으로 본다 |
| 실제 해시가 있고 재계산 값과 다름 | **진짜 불일치** | `tampered` 「변조 감지」 |

**체인 기록을 읽었는데 해시 자리가 비어 있으면 서버가 준 `meta_hash` 로 대신
맞춰보지 않는다.** 통과시켜 봐야 「서버가 준 값끼리」 맞는다는 뜻이라 확인한 것이
없는데, 1단계가 초록으로 남으면 화면이 「확인함」에 가깝게 읽힌다.

온체인 조회 자체를 못 한 경우(API 미구현)는 다르다. 체인에 무엇이 있는지 모르는
상태이므로 서버 값과라도 맞춰보고 `partial` 에 머문다. 이때 상세 화면은 무엇과
비교했는지(`VerificationReport.comparedAgainst`)를 그대로 보여준다 — 대조하지
못했는데 두 해시를 나란히 그리면 비교한 것처럼 읽힌다.

### 3.3 NULL 과 0 을 맞춘 뒤 비교한다

DB 는 값이 없을 때 `NULL`, 체인은 `0` 을 쓴다 (`HASHING.md` §2.1).
이 변환을 빼먹으면 **모든 수입 항목**(`budget_id = NULL`)과
**정정이 아닌 모든 항목**(`corrects_entry_id = NULL`)이 위조로 판정된다.

`registrant`·`approver` 는 체인에 지갑 주소, DB 에 user id 라 값 자체가 다르다.
`User.wallet_address` 매핑을 받아야 비교할 수 있고, 매핑이 없으면
**「모름」으로 남겨 `partial` 이 된다** — 이 두 필드가 「누가 등록하고 누가
승인했는가」의 유일한 온체인 증거이므로 조용히 건너뛰면 안 된다.

**`REJECTED` 항목은 승인자를 비교하지 않는다.** 컨트랙트의 `approver` 는 확정자와
반려자를 겸하는데 DB 에는 반려자 컬럼이 없어, 그대로 비교하면 반려된 항목이 전부
위조로 판정된다. `rejected_by` 컬럼이 생기면 해제한다.

### 3.4 학생 앱은 `canonical()` 을 호출하지 않는다

텍스트는 백엔드가 저장 시점에 한 번만 다듬고 그 값이 정본이다 (`HASHING.md` §1.1).
**API 가 준 값을 앱이 다시 다듬으면 오히려 값이 갈린다.**

`Hashing.canonical()` / `canonicalText()` 는 구현해 두었지만 이는 **총무·감사 앱이
서명용 해시를 직접 만들 때** 쓰라고 둔 것이다 (이승호 파트).

이의 제기(S8)도 마찬가지로 **입력한 원문을 그대로 `POST /objections` 에 보낸다.**
앱이 먼저 다듬으면 지금은 결과가 같더라도 한쪽 로직만 바뀌는 순간 학생이 실제로 친
원문과 저장·해시되는 값이 갈리고, 백엔드의 입력 검증(제어문자 거부, `HASHING.md` §5)이
볼 입력을 앱이 미리 세탁하게 된다. 화면에서 `canonicalText()` 를 쓰는 곳은 최소 길이를
**재기만 하는** 자리 하나뿐이다 — 원문 그대로 길이를 재면 공백 열 칸이 통과한다.

> `String.trim()` 은 쓰지 않는다. Dart 의 `trim()` 은 U+FEFF(BOM)를 지우는데
> Python 의 `strip()` 은 남긴다. 양쪽이 갈리면 해시가 깨진다. NBSP·전각공백·탭도
> 남겨야 한다 — `hashing_vectors.json` 의 `canonical_identity` 벡터가 이를 고정한다.

### 3.5 「OCR 불일치 상태로 승인됨」 뱃지 (S7)

| OCR 상태 | 뱃지 | 이유 |
|:---|:---|:---|
| `MISMATCH` · `DUPLICATE` | 표시 | 경고를 무시하고 승인됨 |
| `NO_NUMBER` · `UNREADABLE` | 없음 | 계좌이체·판독 실패는 정상 경로 |
| `MATCH` | 없음 | — |
| `category_warning` | 표시 | 용도 불일치 소프트 경고 |

경고 승인은 **즉시** 학생에게 노출된다 (PRD §285). 승인자가 입력한 사유도 그대로 보여준다.
**OCR 판독값은 해시에 들어가지 않는다** — 엔진을 교체하면 기존 배지가 전부 깨지기 때문이다.

### 3.6 정정 이력 병합 (S9)

**정정 항목의 `amount` 는 새 총액이 아니라 증감분이다.**
50,000원을 30,000원으로 바로잡으면 정정 항목의 금액은 `-20,000` 이다.
`HASHING.md` §5 가 "음수는 `corrects_entry_id` 가 있을 때만 허용" 이라고 못박은 것이
이 뜻이며, 샘플 3(`amount: -20000`, `purpose: "입력 오류 정정"`)이 같은 형태다.

| 개념 | 규칙 |
|:---|:---|
| 표시 | 원본 금액에 취소선, 최종값 강조. `₩ 50,000 → ₩ 30,000 정정 (입력 오류)` |
| 최종 금액 | `원본 + Σ확정정정` |
| 합계 | **확정 항목을 그냥 다 더한다.** 증감분이라 자연히 최종값이 된다 |
| 대기 중 정정 | 금액에 반영하지 않는다 |

> ⚠️ **김경윤 확인 필요** — 정정 항목이 증감분이 아니라 새 총액을 담는다면
> `EntryChain.finalAmount` 와 `EntryMerge._sumOf` 를 함께 바꿔야 한다.
> 현재는 `HASHING.md` §5 와 샘플 3 을 근거로 증감분으로 구현했다.

**정정 항목도 원본과 똑같이 세 단계를 돌린다.** 원본만 검증하면 안 되는 이유가 셋이다.

1. 정정도 `recordPending` → `confirmEntry` 를 그대로 타는 **독립된 온체인 entry** 이고
   자기 `meta_hash` 를 가진다
2. 화면에 크게 뜨는 **최종 금액이 정정 금액에서 나온다**(`원본 + Σ확정정정`).
   원본만 검증한 배지를 그 숫자 옆에 붙이면, 검증하지 않은 값을 보증하는 셈이 된다
3. 확정된 기록을 고치는 **유일한 통로가 정정이다**(PRD, 규칙 5). 여기가 검증
   사각지대면 「확정 기록은 못 고친다」는 보장이 그대로 우회된다

배지는 체인 전체(`EntryChain.allEntries`)를 합쳐 **나쁜 쪽을 따른다**
(`EntryVerifier.chainStatus`).

| 체인 안의 결과 | 체인 배지 |
|:---|:---|
| 하나라도 `tampered` | `tampered` |
| 전부 `unavailable` | `unavailable` |
| 전부 `verified` | `verified` |
| 그 외 (일부만 확인) | `partial` |

상세 화면의 1·2·3단계 값은 **원본 기준**이고, 정정별 결과는 정정 이력 줄에 배지로
붙는다 — 여러 항목의 해시를 한 카드에 뭉개면 어느 값이 무엇인지 읽을 수 없다.
목록의 「확인 필요」 필터도 정정 쪽 불일치를 잡는다.

### 3.7 `occurred_at` 은 KST 자정이다

사용일의 **KST(Asia/Seoul) 자정**을 Unix 초로 담는다. 시각은 버린다.
`ts % 86400 == 54000` 이 아니면 백엔드가 400 으로 거부한다.

UTC 자정으로 계산하면 9시간이 어긋나 **전날로 밀린다.**
`Hashing.kstMidnightOf(2026, 9, 8)` == `1788793200`.

### 3.8 예산 개정 이력 (S6)

`version > 1` 인 예산에 `v2` 뱃지와 개정 사유를 붙인다.
개정은 **덮어쓰기가 아니라 버전 추가**이므로 이전 버전이 있었다는 사실 자체가 정보다.

> 현재 `BudgetResponse` 에는 이전 버전 금액이 없어, `행사비 200만 → 250만` 중
> **화살표 앞 금액을 표시할 수 없다.** 현재는 `예산 개정 — 250만원 (v2, 참가인원 증가)`
> 형태로만 표시한다. → §5 백엔드 요청사항 참조.

### 3.9 계좌 차액 경고·미등록 건 (S11)

`차액 = 장부잔액 − 계좌 조회 잔액` (PRD §7.4). 차액이 0이 아니거나 미등록 건이
있으면 경고 카드를 띄운다.

**계좌 대조는 한 방향이다.** 조회 결과를 원장에 자동 반영하지 않는다 —
자동으로 맞춰버리면 대조 대상 자체가 사라져 미등록 지출을 영영 못 찾는다.

### 3.10 미확인 항목 뱃지 카운트 (S12)

마지막으로 확인한 항목 id 를 `flutter_secure_storage` 에 저장하고, 그보다 id 가 큰
항목 수를 대시보드 아이콘에 겹쳐 표시한다. 내역 목록을 열면 지워진다.

## 5. 백엔드 연동 현황 및 요청사항

> 담당자에게 넘길 **응답 JSON 형태와 필드 이름은 `docs/backend_requests.md`** 에 있다.
> 이 절은 현황 요약이고, 그 문서가 실제 요청서다.
> `GET /entries/{id}/verify` 에 대한 의견은 `docs/backend_requests_draft_verify.md` 에 따로 있다.

### 5.1 연결 완료

| 엔드포인트 | 쓰는 화면 | 서버 상태 |
|:---|:---|:---|
| `GET /entries` | 대시보드, 내역 목록, 지출 상세 | 목업 3건 (인메모리) |
| `GET /budgets` | 대시보드 예산 카드 | 목업 3건 (`DUMMY_BUDGETS` 상수) |

`GET /balance` 는 서버에 있지만 **일부러 호출하지 않는다.** 장부 잔액은 항목에서
직접 계산한다 (PRD §7.4 「체인 이벤트로 산출, DB 불신뢰」). 서버 값과 대조해
불일치를 표시하는 기능은 후속으로 추가한다.

> ⚠️ **서버 `/budgets` 목업에는 개정된 예산이 없다.** 3건 모두 `version=1` ·
> `revision_reason=null` 이라, 서버에 붙이면 **S6 개정 이력 표시(`v2` 뱃지와 사유)가
> 화면에서 통째로 사라진다** — `version > 1` 일 때만 그리기 때문이다. 서버를 끄고
> 예시 데이터로 볼 때만 보이는 기능이 된다. → `docs/backend_requests.md` §2

### 5.2 아직 없는 엔드포인트 (요청)

| 엔드포인트 | 용도 | 없으면 | 관련 |
|:---|:---|:---|:---|
| `GET /entries/{id}/onchain` | `getEntry(id)` 결과 — 검증 2단계 | 모든 항목이 「부분 검증」에 머문다 | 손종인 |
| `GET /users/wallets` | user id ↔ 지갑 주소 매핑 | 등록자·승인자를 대조하지 못한다 | 손종인 |
| `GET /objections?entry_id=` · `POST /objections` | 이의 제기·답변 (S8) | 화면이 데모 데이터로만 동작 | 김경윤 |
| `GET /memberships/me` | 본인 SBT·QR 페이로드 (S5) | 〃 | 손종인 |
| `GET /snapshots/latest` | 계좌 잔액·미등록 건 (S11) | 〃 | 문승준 |

> **영수증은 바이트 그대로 내려와야 한다.** 재인코딩·EXIF 회전 보정·메타데이터
> 제거를 하면 검증 3단계의 재계산이 깨진다. 썸네일이 필요하면 별도 경로에
> 따로 만들고 원본 경로는 손대지 않는다 (`HASHING.md` §4).

**폴백은 「서버 원장을 보고 있지 않을 때」만 쓴다.** `fetchOnChainEntry` ·
`fetchWalletMap` · `fetchReceiptBytes` 는 `_usingDemoData` 가 참일 때만 데모 값을
돌려주고, 아니면 `null` 로 둔다. 서버 항목에 데모 값을 섞으면 id 만 같고 내용이 다른
것끼리 대조하게 되어 **멀쩡한 항목이 전부 「변조 감지」로 뜬다.** 모르는 것은 채우지
말고 「모름」으로 두어 `partial` 이 되게 한다 (§3.2).

> 🐞 **`fetchLatestSnapshot` 에만 이 가드가 빠져 있다.** 서버가 떠 있으면
> `GET /entries` 는 성공해 `_usingDemoData = false` 가 되고 예시 데이터 배너도
> 사라지는데, `/snapshots/latest` 는 없으니 계좌 잔액만 조용히 데모값(₩ 4,834,000)이
> 된다. 결과적으로 **실제 장부잔액과 가짜 계좌잔액을 비교해, 있지도 않은 「카페베네
> 후문점 미등록 28,000원」 경고가 예시 표시 없이 뜬다.** 반환 타입을
> `SnapshotModel?` 로 바꾸고 다른 셋과 같은 가드를 두면 된다 — 카드가
> `_snapshot != null` 일 때만 그려지므로 화면 쪽은 수정이 필요 없다.

### 6.1 백엔드 목업과의 대조 (`backend_dummy_hash_test.dart`)

`feat/backend-core` 의 목업 더미 3건이 **앱 계산값과 한 바이트도 안 틀린다.**
`occurred_at` 이 KST 자정으로 교체되고 `meta_hash` 가 실제 SHA-256 으로 다시
계산되면서 맞았다. 영수증이 없는 수입 건(#3)도 `receipt_hash` 자리를 빈 문자열로
두고 구분자를 남기는 규칙까지 그대로다.

> ⚠️ **아직 `develop` 에 머지되지 않았다.** 이 테스트가 보는 값의 출처는
> `origin/feat/backend-core` (`a6bdf90`) 이고, `develop` 의 `backend/` 에는 여전히
> `meta_hash="0x456def…"` 자리표시자와 `occurred_at=1757300000` 이 들어 있다.
> **머지 전의 서버에 붙이면 세 건 모두 「변조 감지」(빨강)로 뜬다.**
> 머지되면 이 테스트가 그대로 목업 서버 연동 검증이 된다.

**어제까지의 잠정 구현에서 바뀐 것**

| 항목 | 잠정 (PRD 표기 기준) | 확정 (HASHING.md v1) |
|:---|:---|:---|
| 구분자 | `\|` 파이프 | **U+001F** |
| 결과 표기 | 소문자 hex | **`0x` + 소문자 hex** |
| `occurred_at` | 임의 Unix 초 | **KST 자정 고정** |
| 비교 정규화 | `String.trim()` 사용 | **`trim()` 금지** |
| 검증 범위 | 해시 비교만 | **3단계 전부** |
| 정정 `amount` | 새 총액 | **증감분** |
