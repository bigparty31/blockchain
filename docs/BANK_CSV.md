# 은행 거래내역 CSV 연동

PRD v0.7 §4.6 — 오픈뱅킹 API가 자격 요건상 불가능해져서, 총무가 은행 인터넷뱅킹에서 직접 내려받은 거래내역 파일을 업로드하는 방식으로 계좌 대조를 한다.

## 1. 은행 조사 — NH농협·KB국민

실제 다운로드 파일은 개인 인터넷뱅킹 로그인 후에만 받을 수 있어서, 웹 검색만으로 정확한 컬럼명·순서를 100% 확정하진 못했다. 국내 은행 거래내역 다운로드에 공통적으로 알려진 관례를 근거로 했고, 실제 파일 검증은 TODO로 남는다.

| | NH농협 | KB국민 |
| --- | --- | --- |
| 날짜·시각 | 거래일시 (한 컬럼) | 거래일자 / 거래시각 (두 컬럼) |
| 공통 컬럼 | 적요, 출금액, 입금액, 거래후잔액, 거래점 | 동일 |
| 인코딩 | EUC-KR(CP949)로 내려오는 경우가 많음 — Windows 엑셀 기준 생성이라 UTF-8로 그대로 읽으면 한글 깨짐 | 동일 |

## 2. 파싱 규칙 초안

| 원본 컬럼 | 우리 필드 | 처리 방법 |
| --- | --- | --- |
| 거래일시 / (거래일자+거래시각) | `tran_date`, `tran_time` | 날짜와 시각을 분리해서 저장. 은행이 합쳐서 주면 쪼갠다 |
| 적요 | `description` | 원문 그대로 보존, 가공 없음 |
| 출금액 / 입금액 | `direction`(`IN`/`OUT`) + `amount` | 두 컬럼 중 값이 있는 쪽으로 방향 결정, 금액은 콤마 제거 후 정수 변환. `Entry`의 `kind`(INCOME/EXPENSE)와 그대로 대응시키기 위해 부호 없는 양수로 통일 |
| 거래후잔액 | `balance_after` | 정수 변환만 |

**인코딩 처리**: 업로드된 파일의 **해시는 원본 바이트 그대로** 계산한다(`docs/HASHING.md` §4 — 이미 확정된 규칙과 일치, 인코딩 변환하면 해시가 달라짐). **디코딩(CP949 → 읽을 수 있는 문자열)은 파싱할 때만** 한다 — CP949로 먼저 시도하고 실패하면 UTF-8로 재시도.

## 3. 데모 샘플

`docs/samples/`에 5건짜리 데모 세트를 넣었다. 기준 은행은 NH로 정했다 — 학생회·동아리 계좌가 국내에서 농협을 특히 많이 쓰기 때문이다. KB 포맷도 같은 5건으로 만들어 비교용으로 남겨뒀다.

- `nh_sample.csv` / `kb_sample.csv` — 같은 5건 거래를 각 은행 포맷으로 (UTF-8 저장, 실제 파일은 CP949일 수 있음)
- `normalized_sample.csv` — 파싱 후 정규화된 결과 (2번 항목 매핑 적용)
- `ledger_dummy_entries.csv` — 원장(`Entry`) 더미 데이터. 5건 중 4건과 대응하고, 나머지 1건은 대응하는 Entry가 없다

| 은행 거래 | 원장 | 결과 |
| --- | --- | --- |
| 3/05 입금 10,000 | id 1 | 매칭 |
| 3/10 출금 35,000 | id 2 | 매칭 |
| 3/12 출금 82,000 | id 3 | 매칭 |
| 3/15 입금 50,000 | id 4 | 매칭 |
| 3/18 출금 12,000 (편의점) | 없음 | **미등록** — 계좌에서 돈이 나갔는데 원장엔 없음 |

## 4. 포지셔닝

CSV는 총무가 만들어 올리는 파일이라 위조 가능성이 있다. **"완전한 검증"이 아니라 "등록을 게을리한 누락을 잡는 장치"**로 설명한다. 업로드 파일의 해시를 온체인에 남겨 사후 바꿔치기는 막는다 (PRD §4.6, §13).

## 5. 확인 필요 사항

- PRD §4.6은 "파일 해시를 온체인 기록"이라고 하는데, 최신 `IAccountingLedger.sol`(장석연, develop 병합됨)에는 그 기능을 담당하던 `recordBankSnapshot`이 아예 없어졌다. 파일 해시를 어디에 기록할지 장석연과 확인 필요 — 이번 주 구현 범위는 아니라 지금은 문서화만 해둠
- 실제 NH/KB 인터넷뱅킹 계좌로 파일 1건을 받아서 1번 항목의 컬럼 가정이 맞는지 검증 필요

## 부록 — 구현 단계에서 참고할 것 (이번 주 범위 아님)

아래는 실제 매칭 로직을 구현할 때(§11 5단계) 필요한 설계 메모다. 지금 당장 결정하거나 구현할 필요는 없다.

### 은행별 어댑터 패턴

은행마다 컬럼명·순서·인코딩이 달라서, 은행 원본을 각각 파싱해 2번 항목의 공통 스키마로 변환하는 어댑터를 두고, 매칭 로직은 그 공통 스키마만 보게 하면 은행이 늘어나도 매칭 코드는 안 건드려도 된다.

### 매칭 시 상태별 후보 처리와 중복 케이스

"날짜·금액이 같은 게 하나라도 있으면 매칭"으로 단순하게 짜면, 동일 날짜·금액 거래가 여러 건일 때 개수가 안 맞을 수 있다. 매칭된 `Entry`를 후보 풀에서 소모(consume)하는 방식으로 1:1 대응을 보장해야 한다.

또한 `Entry.status`별로 다르게 다뤄야 한다:
- `CONFIRMED` — 정식 후보. 매칭 안 되면 "미확인_원장항목"(원장엔 있는데 계좌에 대응 거래 없음 — 가짜 등록 의심)으로 표시
- `PENDING` — 보조 후보. 매칭되면 소모하되 "승인대기 중" 정도로만 표시, 강한 의심 딱지는 안 붙임 (아직 감사 전이라 판단 보류)
- `REJECTED`, `BLOCKED` — **후보에서 제외.** 특히 `BLOCKED`(예산 초과로 등록 자체가 거부된 시도)에 대응하는 은행 거래가 있다면 그건 "미등록"으로 잡혀야 정상이다 — 예산 초과 지출을 숨기지 못하게 하는 이 시스템의 핵심 시나리오이므로, 여기서 실수로 매칭 처리해버리면 안 된다

테스트 케이스 아이디어: 동일 날짜·금액 거래 2건 vs 원장 2건(정상 2:2 매칭 확인), 원장엔 있는데 대응 은행 거래가 없는 케이스(미확인_원장항목 확인).

### 참고 — 팀 공유 데모 거래

`docs/hashing_vectors.json`과 `docs/feedback_review.md`(김경윤)가 이미 "한결문구, 35,000원, 2026-09-08" 거래를 공통 데모 예시로 쓰고 있다. 나중에 전체 통합 데모를 만들 때 이 거래를 우리 CSV 대조 데모에도 재사용하면 팀 전체 데모가 하나로 이어진다.
