## 1. 손종인 — 지갑 API

### 반영 완료

`GET /users/wallets` 올려주신 주소로 `_demoWallets`를 맞췄다. 감사 2(user 5)도 추가했다.

`_demoOnChain`이 옛 주소를 **따로 하드코딩해 들고 있어서**, 매핑만 바꿨으면 데모 7건이
전부 "변조 감지"로 뒤집힐 뻔했다. 이제 `_demoWallets`에서 끌어 쓰게 해서 두 군데에
적어두는 구조 자체를 없앴다.

`term`도 온체인 모델(`OnChainEntry.term`)과 검증 비교 목록에 넣었고, `term_id`와
헷갈리지 않게 테스트로 막아뒀다. 다만 `EntryResponse`에 `term_code`가 안 실려 와서
학기 대조는 당분간 "모름"이다 (→ 2절).

### 요청 — 한 사람이 주소를 여러 개 갖는 경우

**이건 앱에서 못 메워서 부탁드립니다.** 지금 응답이 사용자당 주소 하나라, 키를 바꾸면
서버가 새 주소만 주고 옛 주소는 응답에 아예 없습니다. 없는 값을 앱이 만들어낼 수가 없습니다.

**주소 → 사용자 id** 방향(`{"0x3c44…": 2, "0x옛주소…": 2}`)으로 바꾸면 한 사람이 주소를
여러 개 가져도 문제가 없습니다. 앱에서 이 API 쓰는 데가 `fetchWalletMap` 하나뿐이라
지금이 제일 싸고, 실연동(10/7) 붙은 뒤엔 바꿀 데가 늘어납니다.
**바꿔주시면 앱 쪽은 제가 맞추겠습니다.**

> **왜 지금 말하나** — `entry_verifier.dart`의 `_comparePerson`이 `walletByUserId[userId]`로
> **현재 주소 하나**만 꺼내 체인 주소와 비교한다. 키 교체가 일어나면 옛 주소로 등록한
> 과거 항목이 전부 "등록자 불일치 = 변조 감지"로 뜬다. 학생 화면에 빨간 배지가 뜨는 거라
> 조용한 버그가 아니다. 앱 쪽 변경은 `wallet == chainAddress` 비교를
> `userIdByAddress[chainAddress.toLowerCase()] == userId`로 뒤집는 정도로 작다.

### 알림 — `HASHING.md`를 고쳤습니다

§2.3이 아직 병합 전 내용("term을 넣어달라고 요청해 둔 상태")이라, 현재 컨트랙트 기준으로
고쳤습니다. 이미 작업 중이시면 말씀해 주세요 — PR에서 그 파일만 빼겠습니다.

## 2. 김경윤 — `verify` 응답 설계 + `term_code`

**급합니다.** 계획서상 `GET /entries/{id}/verify`가 설계 10/3 · 구현 10/9다.
이번 주에 모양이 굳으면 10/9에 그대로 구현돼서 나중에 다시 요청해야 한다.

`terms.term_code` 넣어주신 거 확인했습니다. `verify` 응답 설계하시는 김에
학생 앱에 필요한 것 세 가지만 같이 봐주시면 좋겠습니다.

### ① 경로가 서로 다릅니다

앱은 지금 `GET /entries/{id}/onchain`을 부르고 있는데 API.md 설계는
`GET /entries/{id}/verify`입니다. **저는 `verify`로 맞추겠습니다** — 확정만 해주세요.

### ② 지금 설계된 응답으로는 검증 2단계를 못 합니다

API.md 초안에 `db_meta_hash` / `onchain_meta_hash` / `is_tampered`만 있는데,
HASHING.md §2가 "해시만 비교하면 반쪽"이라고 한 부분이 통째로 빠집니다.
`meta_hash`는 `kind`·`budget_id`·`term`을 안 덮어서, **수입↔지출 뒤바꾸기나 예산 항목
옮기기는 해시가 한 글자도 안 변합니다.**

`getEntry(id)`가 돌려주는 걸 그대로 담아주시면 됩니다:

```
kind, status, budget_id, corrects_id, occurred_at, term, registrant, approver
```

`is_tampered`는 앱에서 쓰지 않습니다. PRD §7.3이 검증 로직을 앱에 내장하라고 해서,
서버가 "안 바뀌었다"고 말해주는 값은 구조상 믿을 수 없습니다 — 서버가 장악되면 항상
통과를 돌려줄 수 있기 때문입니다. **판단은 앱이 하고, 서버는 원본 값만 주시면 됩니다.**

### ③ `EntryResponse`에 `term_code`

체인의 `Entry.term`은 학기 코드(`20262`)인데 API가 주는 건 행 번호(`term_id = 1`)라
비교할 수 있는 값이 아닙니다. 그냥 비교하면 `1 != 20262`라 **모든 항목이 위조로
판정됩니다.** 한 줄만 추가해 주시면 앱은 고칠 데 없이 바로 돌아갑니다
(`block_number`와 같은 방식으로 받고 있습니다).

## 3. 전원 참고 — 실서버에서 배지가 전부 "부분 검증"으로 뜬다

중간발표 시연 때 질문 나올 수 있어서 적어둔다. **고장이 아니다.**

온체인 조회 API가 아직 없어서 체인 값과 대조 자체를 못 하고 있다.
**확인 못 한 것을 "완전 검증"으로 보여주지 않는다**는 원칙대로 배지가 파랑에 머문다.

- **데모 데이터는 정상 건이 초록으로 뜬다.** 나머지 3건(#3 영수증 바꿔치기, #6 금액 변조,
  #7 예산 항목 옮기기)이 빨강인 것은 **일부러 그렇게 만든 것**이다
- 실서버가 초록이 되려면 셋이 다 필요하다 — ① `verify` 응답에 `getEntry` 필드
  ② `EntryResponse.term_code` ③ 영수증 내려받기. 경윤 구현 10/9
