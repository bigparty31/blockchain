# `GET /entries/{id}/verify` 에 대한 앱 쪽 의견

- **대상**: `feat/backend-core` (김경윤) — `docs/API.md` §2 에 명세된 엔드포인트
- **작성**: 장정아 (앱 — 학생 화면)

> 이 엔드포인트는 **아직 구현 전이고 `API.md` 에 명세만 있는 상태**입니다
> (`origin/feat/backend-core` 기준 `backend/app/routers/` 에 라우트가 없습니다).
> 그래서 「빼 달라」가 아니라 **구현하시기 전에 형태를 정하자**는 의견입니다.

---

먼저 확인된 것부터: **목업 더미 3건의 `meta_hash` 가 앱 계산값과 정확히 일치합니다.**
`occurred_at` 을 KST 자정으로 맞추고 해시를 실제 값으로 다시 계산해 주신 덕분에,
앱이 `docs/HASHING.md` §1 대로 재계산한 값과 한 바이트도 안 틀립니다.
영수증이 없는 수입 건(#3)도 `receipt_hash` 자리를 빈 문자열로 두고 구분자를 남기는
규칙까지 그대로 맞습니다. 이전 더미는 자리만 채운 값이라 앱에서 전부
「변조 감지」로 떴는데, 이제 목업만으로 검증 화면을 제대로 확인할 수 있습니다.

앱 쪽에 `app/test/backend_dummy_hash_test.dart` 로 고정해 두었습니다 — 규격이 다시
갈리면 앱 테스트가 먼저 깨집니다. 다만 **이 커밋(`a6bdf90`)이 `develop` 에 머지되어야**
목업 서버로 검증 화면을 볼 수 있습니다. `develop` 의 더미는 아직 자리표시자라
지금 붙이면 세 건 모두 빨강으로 뜹니다.

## 요청: `GET /entries/{id}/verify` 의 `is_tampered` 는 앱이 쓰지 않겠습니다

응답에 서버가 판정한 `is_tampered` 가 들어 있는데, 학생 화면은 이 값을 **읽지 않고
자체 계산 결과만 표시**할 예정입니다. 엔드포인트를 빼 달라는 게 아니라, 앱이 왜
안 쓰는지 남겨두려는 것입니다.

이유는 PRD §7.3 의 신뢰 경계입니다. 이 시스템에서 학생이 최종적으로 의심해야 하는
대상에는 **서버도 포함**됩니다. 서버가 계산해서 내려준 "변조 없음"을 그대로 배지로
띄우면, 서버가 값을 바꾼 경우 학생이 그것을 알 방법이 사라집니다. 앱이 직접
SHA-256 을 돌려 온체인 값과 대조하는 구조라야 그 경우가 잡힙니다.
(앱 쪽 근거는 `docs/student_screens.md` §3.4 에 적어두었습니다.)

## 대신 `hash_inputs` 는 매우 유용합니다 — 이건 쓰겠습니다

```json
"hash_inputs": {
  "amount": "35000",
  "counterparty": "한결문구",
  "purpose": "신입생 환영회 명찰 및 필기구 구매",
  "occurred_at": "1788793200",
  "receipt_hash": "0xabc…"
}
```

앱 계산값과 온체인 값이 어긋났을 때, **어느 필드에서 갈렸는지** 짚어주는 용도로
쓰겠습니다. 지금은 불일치가 나도 "안 맞는다"까지만 보이고 원인을 못 짚는데,
이 필드가 있으면 상세 화면에서 갈린 항목을 바로 표시할 수 있습니다.

정리하면 **판정은 앱이, 원인 표시는 `hash_inputs` 로** 나눠 쓰겠습니다.

## 확인 부탁드리는 것 하나

`hash_inputs` 의 값이 **정본화(canonical) 를 거친 뒤의 값**인지, DB 원본 그대로인지
알려주시면 좋겠습니다. `HASHING.md` §1.1 상 텍스트 정본화는 백엔드가 저장 시점에
한 번만 하고 그 값이 정본인데, `hash_inputs` 가 정본화 **이전** 값이라면 앱이
그것으로 다시 계산했을 때 서버와 다른 해시가 나옵니다. 그러면 원인 표시용으로
쓰려던 게 오히려 오탐을 만듭니다.
