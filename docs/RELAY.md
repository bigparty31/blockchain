# RELAY — 등록·확정·반려 릴레이

작성 손종인 · 대상 김경윤(등록·승인 API·ERD), 이승호(등록·승인 화면·서명) · 코드 `backend/app/relay/` · 테스트 `backend/tests/test_registration_relay.py`, `test_decision_relay.py`

총무 서명은 id를 알아야 만들 수 있고, id는 저장해야 생긴다 (CHAIN_CLIENT §1). 그래서 **체인에 올리기 전 값은 Entry가 아니라 초안 테이블에 둔다.** Entry에는 체인에 올라간 항목만 들어간다.

| | Entry | 초안 |
| --- | --- | --- |
| 들어가는 것 | 체인에 기록된 항목 | 서명 대기·제출 중·실패·버림 |
| `status` | 지금 그대로 (PENDING·CONFIRMED·REJECTED·BLOCKED). NULL 없음 | `DraftStatus` (§2) |
| 읽는 곳 | 학생 앱·목록·잔액·결산·검증 | 총무의 미제출 초안 화면 |

등록(§1~§6)과 확정·반려(§9)는 코드와 테스트로 구현돼 있다. **§7과 §9의 API 모양은 제안이고, §8은 상의할 것이다.** 라우터·DB·대조 주기 실행은 §8이 정해진 뒤 연결한다.

---

## 1. 흐름

```
① 앱 → 서버   입력값
              서버: 검증 · 정규화 · meta_hash 계산 · OCR · 영수증 저장
                    → open_draft: Entry 시퀀스에서 id 예약 · 초안 저장(DRAFT)  →  id + 서명할 값
② 앱          RecordRequest 구성 (meta_hash 는 직접 계산, deadline 은 앱이 정함) · 생체인증 서명
③ 앱 → 서버   meta_hash + deadline + 서명
              서버: submit → 해시·시한·서명자 확인 → SUBMITTING 저장 → record_pending
                    → 성공 RECORDED + Entry 생성  /  revert FAILED  /  연결 실패 SUBMITTING 유지
대조          reconcile (주기 실행): SUBMITTING 초안을 체인과 맞춰 RECORDED 또는 FAILED 로
```

```python
from functools import partial
from app.chain import Eip712Domain, recover_signer
from app.relay import RegistrationRelay

domain = Eip712Domain(chain_id=80002, verifying_contract=LEDGER_ADDRESS)
relay = RegistrationRelay(chain, draft_store, partial(recover_signer, domain))
# 테스트: RegistrationRelay(FakeChainClient(), InMemoryDraftStore(), fake_recover_signer)
```

## 2. 초안 상태

| 상태 | 뜻 | 다시 서명 | 버리기 |
| --- | --- | --- | --- |
| `DRAFT` | 서명 대기 | ○ | ○ |
| `SUBMITTING` | 체인에 보냈고 결과를 모름. **다시 보내지 않는다** | ✕ | ✕ |
| `FAILED` | 체인에 없는 것이 확정됨 (`fail_reason`) | ○ | ○ |
| `RECORDED` | 체인에 들어갔고 Entry가 생김 (`entry_status` = `PENDING`·`BLOCKED`) | ✕ | ✕ |
| `DISCARDED` | 총무가 버림. 예약한 id는 다시 쓰지 않는다 | ✕ | ✕ |

`fail_reason`

- `RevertReason` 값 (`NotRegistrant`, `SignatureExpired` 등) — 체인이 거부했다
- `NotSent` — 보내지 못했다 (잔고 부족·연결 실패 등). 체인에 없는 것이 확정이라 **바로 다시 제출할 수 있다**
- `NotRecordedByDeadline` — 서명 시한이 지나도록 체인에 없다
- `EntryIdTaken` — 체인에 같은 id가 다른 내용으로 있다. DB만 초기화하고 체인은 그대로일 때 생긴다. **다시 서명해도 같으므로 버리고 새 초안으로 등록한다**

## 3. ① 초안 만들기 — `open_draft`

체인에 올리면 revert 되거나 막힐 값은 **id를 예약하기 전에** `INVALID_DRAFT`로 막는다.

- 금액 0, 정정이 아닌데 음수
- 예산 없는 지출 — 체인에 올리면 `BLOCKED(BUDGET_NOT_FOUND)`
- 예산이 붙은 수입
- 해시·`occurred_at`·주소 형식

`budget_id`·`corrects_id`는 DB처럼 없으면 `None`으로 넘긴다. 체인에는 0으로 간다 (HASHING §2.1).

정정 대상이 있는지·확정됐는지, 예산 잔량은 여기서 보지 않는다. DB·체인 상태가 필요하므로 등록 API가 본다.

## 4. ③ 제출 — `submit`

확인 순서와 실패 코드. 여기서 막히면 체인에는 아무것도 가지 않고 초안도 그대로다.

| 순서 | 확인 | 실패 코드 |
| --- | --- | --- |
| 1 | 초안이 있다 | `DRAFT_NOT_FOUND` |
| 2 | `SUBMITTING`·`RECORDED`면 **보내지 않고 지금 상태를 돌려준다** | — |
| 3 | 버린 초안이 아니다 | `DRAFT_DISCARDED` |
| 4 | 앱의 `meta_hash` == 서버 값 | `HASH_MISMATCH` |
| 5 | `지금 < deadline ≤ 지금 + 600초` | `INVALID_DEADLINE` |
| 6 | 서명에서 주소를 복구할 수 있다 | `INVALID_SIGNATURE` |
| 7 | 복구한 주소 == 초안의 총무 주소 (소문자로 비교) | `SIGNER_MISMATCH` |
| 8 | 롤 조회(`roles=`)를 붙였으면 그 주소에 `TREASURER` 롤이 있다 | `ROLE_MISSING` |

- 4는 원인을 바로 짚어 준다 — 어긋나면 대부분 정규화 차이다 (HASHING §1.1)
- 7은 해시에 들어가지 않는 `kind`·`budget_id`·`corrects_id`·`deadline`까지 막는다. 서버가 **초안 값으로 struct를 다시 만들어** 서명자를 복구하기 때문이다. 앱이 한 필드라도 다르게 서명하면 다른 주소가 나온다
- 8은 선택이다. `RegistrationRelay(..., roles=services.roles)`로 붙이면 롤이 없는 서명을 가스를 쓰기 전에 막고, 체인의 `NotRegistrant`는 "보낸 사이 롤이 바뀜"으로만 남는다. 롤을 읽다 연결이 끊기면 `ChainUnavailable`을 그대로 올리고 초안은 그대로다
- 2와 `DraftStore.transition`이 **같은 초안을 두 번 보내지 않는 장치**다. 앱이 타임아웃으로 재시도하거나 두 요청이 동시에 와도 체인에는 한 번만 간다

체인 결과에 따른 처리:

| 결과 | 초안 | Entry |
| --- | --- | --- |
| `TxResult` | `RECORDED` | 생성 (`status`, `tx_pending`) |
| `ChainRevert` | `FAILED`, `fail_reason` = 에러 이름 | 없음 |
| `ChainNotSent` | `FAILED(NotSent)` | 없음 |
| `ChainRevert(ENTRY_ALREADY_EXISTS)` | 체인 값과 대조 — 같으면 `RECORDED`, 다르면 `FAILED(EntryIdTaken)` | 같을 때만 생성 |
| `ChainUnavailable` | `SUBMITTING` 유지, 대조가 마무리 | 아직 없음 |

## 5. 대조 — `reconcile`

`SUBMITTING` 초안마다:

1. `get_entry(id)`가 있고 해시·등록자가 초안과 같으면 → `get_record_result(id)`로 tx 해시·BLOCKED 사유를 찾아 `RECORDED`
2. 있는데 내용이 다르면 → `FAILED(EntryIdTaken)`
3. 없고 `deadline + 120초`가 지났으면 → `FAILED(NotRecordedByDeadline)`
4. 그 밖에는 다음 번에 다시 본다. 체인 연결이 안 되면 그 초안은 건너뛴다

**3이 안전한 이유** — 컨트랙트는 시한이 지난 서명을 `SignatureExpired`로 거부한다. 시한이 지났는데 체인에 없으면 앞으로도 들어갈 수 없다. 120초는 블록 시각 오차에 대한 여유다.

서버가 응답을 기다리다 죽어도 `SUBMITTING`이 먼저 저장돼 있으므로 대조가 이어받는다. 주기는 30초~1분이면 충분하고, `app/relay/runner.py`의 `run_periodically`로 돌린다 (CHAIN_CLIENT §6.3). 연결 실패 뒤 총무가 다시 서명할 수 있을 때까지는 최대 `deadline + 120초`가 걸린다.

## 6. DraftStore — DB 구현이 지킬 것

코드에는 테스트용 `InMemoryDraftStore`만 있다. 실제 구현은 ERD와 함께 정한다 (§8).

- **`reserve_id`** — Entry id 시퀀스에서 받는다 (`SELECT nextval(pg_get_serial_sequence('entry', 'id'))`). 그래서 Entry.id 칼럼은 값을 직접 넣을 수 있어야 한다 — `SERIAL` 또는 `GENERATED BY DEFAULT AS IDENTITY` (`ALWAYS`는 안 됨)
- **`transition`** — 확인과 변경을 한 문장으로. `UPDATE draft SET ... WHERE id = :id AND status IN (...) [AND signature = :sig] RETURNING *`. 대조는 서명까지 맞출 때만 실패로 바꾼다 — 읽어 둔 제출이 그사이 실패하고 새 서명으로 다시 제출됐으면 새 제출을 건드리지 않기 위해서다
- **`record`** — 초안의 `RECORDED` 전환과 Entry INSERT를 **한 DB 트랜잭션**으로. 초안이 `SUBMITTING`이 아니면 아무것도 하지 않는다
- 버린·실패한 초안의 id는 체인에 없다. Entry id에 빈 번호가 생기는 것이 정상이다

초안 테이블 칼럼 (제안) — Entry 입력 칼럼 전부(`term_id`, `kind`, `amount`, `counterparty`, `purpose`, `budget_id`, `occurred_at`, `receipt_path`, `receipt_hash`, `meta_hash`, OCR 칼럼, `category_warning`, `corrects_entry_id`, `correction_reason`, `created_by`) + `registrant`, `status`, `deadline`, `signature`, `fail_reason`, `tx_hash`, `created_at`, `updated_at`.

## 7. API 모양 (제안)

경로·이름은 김경윤이 정한다. 아래는 서비스가 주고받는 값을 옮긴 예시다.

**① 초안 만들기** — 응답에 서명할 값과 EIP-712 도메인을 함께 내려준다.

```
POST /entries/drafts            요청 본문은 지금의 POST /entries 와 같다

201
{
  "id": 42,
  "status": "DRAFT",
  "sign": {
    "domain":  { "name": "AccountingLedger", "version": "1", "chainId": 80002, "verifyingContract": "0x..." },
    "message": { "id": 42, "hash": "0x...", "amount": 35000, "kind": 1,
                 "occurredAt": 1789743600, "budgetId": 2, "correctsId": 0 }
  }
}
```

앱은 `message.hash`를 그대로 서명하지 않고 **직접 계산한 값과 같은지 먼저 본다.** `deadline`은 앱이 정해 `message`에 넣는다 (제안: 지금 + 300초).

**③ 제출**

```
POST /entries/drafts/42/submit
{ "meta_hash": "0x...", "deadline": 1790000300, "signature": "0x..." }

200  { "id": 42, "status": "RECORDED", "entry_status": "PENDING", "tx_hash": "0x..." }
200  { "id": 42, "status": "SUBMITTING" }                         결과 모름. 잠시 뒤 GET 으로 확인
200  { "id": 42, "status": "FAILED", "fail_reason": "NotRegistrant" }
400  { "code": "SIGNER_MISMATCH", "detail": "..." }               §4 표의 사전 확인 실패
404  { "code": "DRAFT_NOT_FOUND" }
409  { "code": "DRAFT_DISCARDED" }
```

revert·연결 실패는 요청을 처리한 결과라 200에 상태로 담는다. 400대는 체인에 보내기 전에 막힌 경우만이다.

**그 밖에**

```
GET    /entries/drafts         내 DRAFT·SUBMITTING·FAILED 초안
GET    /entries/drafts/42      초안 하나 (SUBMITTING 확인용)
DELETE /entries/drafts/42      버리기. DRAFT·FAILED 만 (그 밖에는 409 CANNOT_DISCARD, 남의 초안은 403 NOT_OWNER)
```

## 8. 상의할 것

| 무엇 | 누구와 | 왜 |
| --- | --- | --- |
| API 경로·응답 모양 (§7, §9) | 김경윤, 이승호 | 지금 `POST /entries`는 바로 PENDING을 돌려준다. 초안 방식으로 바꾸면 앱 등록 화면이 두 번 호출하는 흐름이 된다 |
| 초안·결정 테이블과 Entry.id 칼럼 (§6, §9) | 김경윤 | ERD 담당. id를 시퀀스에서 예약하므로 Entry.id 정의가 정해진다. 결정 테이블에는 부분 유니크 인덱스가 필요하다 |
| 반려자 칼럼 `rejected_by` | 김경윤 | 반려가 체인에 들어가도 DB에 반려자를 남길 곳이 없다. 검증에서 `REJECTED`의 `approver`를 대조하지 못한다 (HASHING §8) |
| **OCR 중복 검사에 열린 초안 포함** | 김경윤 | 빠지면 같은 영수증으로 만든 초안 둘이 모두 체인에 올라가고, 두 번째 Entry INSERT가 유니크 인덱스 `(ocr_approval_no, ocr_paid_at, amount)`에 걸린다. 그 초안은 `SUBMITTING`에서 빠져나오지 못하고 대조도 매번 같은 곳에서 멈춘다 |
| `deadline` 값 | 이승호 | 제안: 앱은 지금 + 300초, 서버는 600초까지 받는다 |
| 확정 시 예산 만료 (`BUDGET_EXPIRED`) | 장석연 | 등록 뒤 확정 전에 예산이 마감되면 확정이 revert 된다. 반려 흐름으로 보낼지, 컨트랙트가 등록 시점 기준으로 소모를 허용할지 |
| 승인 전 수정 | 팀 | PRD §4.3은 "승인 전 수정은 매번 새 Pending"이다. 이 설계에서 수정은 새 초안·새 id인데, 이전 PENDING 항목을 반려로 닫을지 정정처럼 이을지 |
| 빈 id 표시 | 학생 화면 담당 | 버린·실패한 초안의 id는 체인에 없다. 화면에 id가 순번처럼 보이면 "숨긴 항목"으로 오해할 수 있다 |

## 9. 확정·반려 — `DecisionRelay`

항목이 이미 체인에 있으므로 id 예약·초안이 없다. **제출 한 번이 `Decision` 하나**이고, 실패한 뒤 다시 내면 새 `Decision`이다.

```python
relay = DecisionRelay(chain, decision_store, partial(recover_signer, domain))

await relay.confirm(entry_id, decided_by=user_id, approver=wallet, meta_hash=..., had_warning=False,
                    warning_reason_hash=ZERO_BYTES32, deadline=..., signature=...)
await relay.reject(entry_id, decided_by=user_id, approver=wallet, reason_hash=..., deadline=..., signature=...)
await relay.reconcile()  # 등록 릴레이와 같은 주기로
```

| 상태 | 뜻 |
| --- | --- |
| `SUBMITTING` | 체인에 보냈고 결과를 모름. **이 항목에 다른 결정을 보내지 않는다** |
| `FAILED` | 체인에 반영되지 않은 것이 확정됨 (`fail_reason`). 새 결정을 낼 수 있다 |
| `RECORDED` | 체인에 들어갔고 Entry가 `CONFIRMED`·`REJECTED`로 바뀜 |

**한 항목에 결정 하나** — 그 항목에 `SUBMITTING`·`RECORDED` 결정이 있어도 요청 자체(시한·서명자·롤)는 먼저 확인한다. 통과하면 **같은 승인자가 같은 내용으로 다시 낸 요청**만 보내지 않고 그 결정을 돌려준다. 다른 승인자이거나 내용이 다르면(반대 결정 포함) `DECISION_IN_PROGRESS`(제출 중) 또는 `ALREADY_DECIDED`(끝남)로 막는다 — 남의 결정을 자기 결정처럼 돌려주지 않는다. 확정과 반려가 동시에 와도 체인에는 하나만 간다. `DecisionStore.begin`이 확인과 삽입을 한 번에 한다 — 부분 유니크 인덱스 `(entry_id) WHERE status IN ('SUBMITTING', 'RECORDED')`.

**보내기 전 확인**

| 확인 | 실패 코드 |
| --- | --- |
| 경고 승인이면 사유 해시가 있다, 경고가 없으면 `bytes32(0)`이다, 반려는 사유가 있다 | `INVALID_REASON` |
| 주소·해시 형식 | `INVALID_DECISION` |
| 체인에 항목이 있다 | `ENTRY_NOT_FOUND` |
| 체인에서 `PENDING`이다 (`BLOCKED`는 확정·반려할 수 없다) | `ENTRY_NOT_PENDING` |
| 승인자 ≠ 체인의 등록자 | `SELF_APPROVAL` |
| 확정: 앱의 `meta_hash` == 체인 항목의 `hash` | `HASH_MISMATCH` |
| `지금 < deadline ≤ 지금 + 600초` | `INVALID_DEADLINE` |
| 서버가 만든 struct로 복구한 서명자 == 승인자 주소 | `INVALID_SIGNATURE` · `SIGNER_MISMATCH` |
| 롤 조회(`roles=`)를 붙였으면 승인자에게 `AUDITOR`·`PRESIDENT` 중 하나가 있다 | `ROLE_MISSING` |

- 확인하려고 체인을 읽다가 연결이 끊기면 `ChainUnavailable`을 그대로 올린다. 아무것도 저장하지 않았으니 다시 요청하면 된다
- 항목에 경고가 있는지(OCR 불일치·카테고리 경고)는 DB 값이라 **호출하는 쪽이 보고 `had_warning`을 정한다**
- 롤 조회를 붙이지 않으면 승인자 역할은 체인이 `NOT_APPROVER`로 거부한다

**체인 결과**

| 결과 | 결정 | Entry |
| --- | --- | --- |
| `TxResult` | `RECORDED` | 갱신 |
| `ChainRevert` | `FAILED`, `fail_reason` = 에러 이름. `InsufficientBudget`이면 앱이 반려 흐름으로 넘긴다 | 그대로 |
| `ChainNotSent` | `FAILED(NotSent)`. 반대 결정도 바로 낼 수 있다 | 그대로 |
| `ChainRevert(INVALID_STATUS)` | 확인과 전송 사이에 체인에서 결정이 났다 — 아래 대조 규칙으로 판정 | 이 결정대로 끝났을 때만 갱신 |
| `ChainUnavailable` | `SUBMITTING`, 대조가 마무리 | 아직 그대로 |

**대조** — `SUBMITTING` 결정마다 체인 항목을 읽는다.

1. 이 결정대로 끝났다 (같은 status·같은 승인자) → `get_decision_result`로 tx 해시를 찾아 `RECORDED`
2. 다르게 끝났다 (반대 결정·다른 승인자) → `FAILED(DecidedElsewhere)`
3. 아직 `PENDING`이고 `deadline + 120초`가 지났다 → `FAILED(NotRecordedByDeadline)`

**`DecisionStore.record`** — 결정의 `RECORDED` 전환과 Entry 갱신을 **한 DB 트랜잭션**으로. 확정은 `status = CONFIRMED`, `approved_by`, `warning_ack_reason`, `tx_confirm`. 반려는 `status = REJECTED`, `reject_reason`, `tx_confirm` (반려자 칼럼은 §8).
